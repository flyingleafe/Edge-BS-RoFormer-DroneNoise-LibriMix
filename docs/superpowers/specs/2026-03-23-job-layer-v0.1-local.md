## 1. Local GPU Scheduler

The box has 2 GPUs. The scheduler is a simple **job queue** that assigns jobs to free GPUs.

### Rules

- Each job claims 1 GPU (or more if `gpu_count > 1`).
- If no GPU is free, the job is **queued** and starts when one becomes available.
- Jobs run as `nohup` background processes tracked by PID in the DB. No daemon — `postdoc job submit` launches the process directly. When a job finishes, a completion hook checks for queued jobs and launches the next one.
- GPU allocation is tracked in the local SQLite DB.

### State Machine (simplified)

```
DEFINED → SUBMITTED → QUEUED → TRAINING → EVAL → DONE
                                   |          |
                                 FAILED     FAILED
```

No LOCAL_REPRO / FIXING / RESUBMITTED / ESCALATED states in v0.1. On failure, the job goes to FAILED with logs saved, and you (or an agent) inspect and fix manually.

## 2. Execution Backend

### How a Job Runs

`postdoc job submit experiments/foo.yaml`:

1. Parse experiment YAML, merge `base_config` + `overrides` into resolved config.
2. Auto-commit to `exp/<experiment-name>` branch (same as full design).
3. Find a free GPU. If none, mark job as QUEUED.
4. When GPU is available, launch a **wrapper script** (`src/postdoc/run_job.py`) via `nohup`. The wrapper handles training → eval → metrics extraction → queue drain sequentially:

**Training:**
```bash
CUDA_VISIBLE_DEVICES=<gpu_id> python train.py \
  --model_type <model_type> \
  --config_path <resolved-config-path> \
  --data_path <data-path> [<data-path-2> ...] \
  --results_path results/<job-id>/training \
  --valid_path <valid-path> \
  --device_ids 0
```

**Eval:**
```bash
CUDA_VISIBLE_DEVICES=<gpu_id> python final_valid.py \
  --model_type <model_type> \
  --config_path <resolved-config-path> \
  --start_check_point results/<job-id>/training/checkpoints/<best_or_last>.ckpt \
  --valid_path <valid-path> \
  --store_dir results/<job-id>/eval/samples \
  --device_ids 0
```

5. On eval completion, the wrapper parses eval stdout to extract metrics (SI-SDR, PESQ, STOI, SDR) into `results/<job-id>/eval/metrics.json`. If parsing fails, `meta.json` is flagged `metrics_incomplete: true`.
6. Mark DONE, release GPU, check for queued jobs and launch the next one.

### model_type resolution

The experiment YAML includes an explicit `model.type` field:

```yaml
model:
  type: dcunet                                    # passed directly as --model_type
  base_config: configs/5_Baseline_dcunet.yaml
  overrides:
    training.lr: 3.0e-4
```

This is simpler than inferring from the config file and avoids ambiguity. The `model.type` field is also used in the full design.

### Multi-dataset support

`dataset.name` can be a string or a list. A list is passed as multiple `--data_path` arguments:

```yaml
dataset:
  name: [dregon-v1, dn-lm-v2]    # resolves to multiple --data_path args
```

### Process Management

The wrapper script (`run_job.py`) is launched via `nohup` with PID tracked in the DB. Stdout/stderr are captured to `results/<job-id>/training/logs/` and `results/<job-id>/eval/logs/`.

If the SSH session drops, running jobs continue (via `nohup`). The DB tracks PIDs so `postdoc job status` can check if a process is still alive.

When the wrapper finishes (success or failure), it updates the DB and checks for queued jobs. If a GPU is now free and jobs are queued, it launches the next one. This eliminates the need for a persistent daemon.

## 3. Results (Local Filesystem)

Same directory structure as the full design's R2 layout, but local:

```
results/
  <job-id>/
    config.yaml          # frozen resolved config
    commit.txt           # git commit hash + experiment branch
    training/
      checkpoints/       # periodic + final
      logs/              # stdout/stderr
      wandb_run_id.txt
    eval/
      metrics.json       # { si_sdr, pesq, stoi, sdr }
      samples/           # enhanced audio examples
    meta.json            # state, timestamps, GPU used
```

When the full layer is implemented, these local results can be bulk-uploaded to R2 with `postdoc results push`.

## 4. CLI (v0.1 subset)

```bash
postdoc job submit <experiment.yaml>         # resolve config, queue, run on next free GPU
postdoc job submit experiments/*.yaml        # batch: queue all, run as GPUs free up
postdoc job list [--state queued|running|done|failed]
postdoc job status <job-id>                  # state, GPU, PID, W&B link, latest metrics
postdoc job logs <job-id> [--tail]           # cat/tail the log files
postdoc job cancel <job-id>                  # kill process, release GPU
postdoc results show <job-id>               # print metrics.json
postdoc results compare <id1> <id2> ...     # side-by-side metrics table
```

Not implemented in v0.1: `postdoc cost *`, `postdoc job retry`, `postdoc results export`, `postdoc results sync`.

## 5. Package Structure (v0.1)

```
src/postdoc/
  __init__.py
  cli.py                  # Typer CLI
  config.py               # Load postdoc.yaml + experiment YAMLs
  experiment.py            # Parse experiment YAML, merge configs
  scheduler.py             # GPU allocation, job queue, process management
  db.py                    # SQLite: jobs table, GPU allocation
  results.py               # Metrics extraction, comparison
```

No `skypilot.py`, `r2.py`, `cost.py`, or `lifecycle.py` in v0.1. These are added when upgrading to the full design.

## 6. Global Config (v0.1)

```yaml
# postdoc.yaml
gpus: 2                    # number of local GPUs

wandb:
  project: harmonic-noise-suppression
  entity: <wandb-username>

results_dir: results       # local results directory
data_dir: datasets         # where datasets live locally
```

No `storage`, `compute.clouds`, or `notifications` sections in v0.1.

## 7. Migration Path to Full Design

v0.1 → full design is additive:

1. Add `skypilot.py`, `r2.py`, `cost.py` — new backends, same interface.
2. `scheduler.py` gets a `CloudScheduler` alongside `LocalScheduler`. The CLI dispatches to the right one based on `resources.cloud` in the experiment YAML (local if omitted or `local`, cloud otherwise).
3. Bulk upload existing local results to R2: `postdoc results push --all`.
4. Add failure handling states to the state machine.
5. Experiment YAMLs stay identical — a job written for v0.1 works on the full layer.
