# Job Layer v0.1 — Local Backend + Abstract Interfaces

**Date:** 2026-03-23
**Status:** Reviewed — awaiting user approval
**Scope:** Abstract interfaces for the job layer (storage, scheduler, job tracker) plus the local backend implementation. Designed so local and cloud backends are interchangeable via config or env var.

## Design Principle

The train/eval code, CLI, and agents interact **only with abstract interfaces**. The backend (local vs cloud) is selected at startup via `postdoc.yaml` or `POSTDOC_BACKEND=local|cloud` env var. All Python code that touches storage, job submission, or results goes through these interfaces — never directly to the filesystem or SkyPilot.

```
┌─────────────────────────────────────────────────┐
│  CLI / Agent / train.py / final_valid.py        │
└──────────────────┬──────────────────────────────┘
                   │ (abstract interfaces)
        ┌──────────┼──────────┐
        ▼          ▼          ▼
  StorageBackend  Scheduler  JobTracker
        │          │          │
   ┌────┴────┐  ┌──┴──┐   (shared SQLite
   │         │  │     │    impl for both)
 Local    R2  Local  Cloud
```

## 1. Abstract Interfaces

### 1.1 StorageBackend

Handles all artifact I/O: checkpoints, logs, configs, metrics, audio samples.

```python
from abc import ABC, abstractmethod
from pathlib import Path, PurePosixPath
from typing import BinaryIO, Iterator

class StorageBackend(ABC):
    """Unified interface for reading/writing job artifacts."""

    @abstractmethod
    def put(self, job_id: str, rel_path: PurePosixPath, data: bytes | BinaryIO) -> None:
        """Write an artifact. rel_path is relative to the job root,
        e.g. 'training/checkpoints/epoch_10.ckpt'"""

    @abstractmethod
    def get(self, job_id: str, rel_path: PurePosixPath) -> bytes:
        """Read an artifact."""

    @abstractmethod
    def get_to_file(self, job_id: str, rel_path: PurePosixPath, dest: Path) -> None:
        """Download an artifact to a local file path."""

    @abstractmethod
    def list(self, job_id: str, prefix: PurePosixPath | None = None) -> list[PurePosixPath]:
        """List artifacts under a job, optionally filtered by prefix."""

    @abstractmethod
    def exists(self, job_id: str, rel_path: PurePosixPath) -> bool:
        """Check if an artifact exists."""

    @abstractmethod
    def put_json(self, job_id: str, rel_path: PurePosixPath, data: dict) -> None:
        """Write a JSON artifact (convenience)."""

    @abstractmethod
    def get_json(self, job_id: str, rel_path: PurePosixPath) -> dict:
        """Read a JSON artifact (convenience)."""

    @abstractmethod
    def job_root_path(self, job_id: str) -> str:
        """Return the human-readable location of a job's artifacts
        (local path or r2:// URI). For display/logging only."""
```

**Local implementation:** reads/writes to `<results_dir>/<job-id>/...` on the local filesystem.
**Cloud implementation:** reads/writes to `r2://postdoc/jobs/<job-id>/...` via boto3 S3-compatible client.

### 1.2 Scheduler

Handles job execution: submitting work to compute, cancelling, and checking process liveness.

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class SchedulerSubmitResult:
    """Returned by scheduler.submit()."""
    process_handle: str       # PID (local) or SkyPilot job ID (cloud)
    gpu_ids: list[int]        # which GPUs were allocated (local) or logical IDs (cloud)

class Scheduler(ABC):
    """Manages compute allocation and job execution."""

    @abstractmethod
    def submit(self, job_id: str, resolved_config: Path, experiment: dict) -> SchedulerSubmitResult:
        """Launch training+eval for this job. Returns a handle for tracking."""

    @abstractmethod
    def cancel(self, job_id: str, process_handle: str) -> None:
        """Kill a running job and release its resources."""

    @abstractmethod
    def is_alive(self, process_handle: str) -> bool:
        """Check if the process/instance is still running."""

    @abstractmethod
    def available_capacity(self) -> int:
        """Number of GPUs (local) or instances (cloud) available for new jobs."""

    @abstractmethod
    def drain_queue(self, tracker: "JobTracker") -> None:
        """Check for queued jobs and launch them if capacity is available.
        Called after a job completes or is cancelled."""
```

**Local implementation:** manages GPU allocation via CUDA_VISIBLE_DEVICES, launches nohup processes, tracks PIDs.
**Cloud implementation:** compiles SkyPilot tasks, launches instances, manages teardown.

### 1.3 JobTracker

Tracks job state, metadata, and provides query capabilities. **Single implementation** (SQLite) used by both backends.

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass
from datetime import datetime
from enum import Enum

class JobState(Enum):
    DEFINED = "defined"
    SUBMITTED = "submitted"
    QUEUED = "queued"
    TRAINING = "training"
    EVAL = "eval"
    COMPLETING = "completing"
    DONE = "done"
    FAILED = "failed"
    # Full design adds: LOCAL_REPRO, FIXING, RESUBMITTED, ESCALATED

@dataclass
class JobRecord:
    job_id: str
    experiment_name: str
    state: JobState
    git_branch: str
    git_commit: str
    process_handle: str | None
    gpu_ids: list[int] | None
    submitted_at: datetime
    started_at: datetime | None
    completed_at: datetime | None
    failed_at: datetime | None
    error_category: str | None
    error_message: str | None
    metrics: dict | None           # populated after eval
    metrics_incomplete: bool
    wandb_run_id: str | None
    config_snapshot: dict           # frozen resolved config

class JobTracker:
    """SQLite-backed job state tracking. Shared across backends."""

    def create_job(self, experiment_name: str, config: dict, git_branch: str, git_commit: str) -> str:
        """Create a new job record in DEFINED state. Returns job_id."""

    def update_state(self, job_id: str, state: JobState, **fields) -> None:
        """Transition job to a new state, updating relevant fields."""

    def get_job(self, job_id: str) -> JobRecord:
        """Get a single job record."""

    def list_jobs(self, state: JobState | None = None, limit: int = 50) -> list[JobRecord]:
        """List jobs, optionally filtered by state."""

    def get_queued_jobs(self) -> list[JobRecord]:
        """Get all QUEUED jobs in submission order."""

    def set_metrics(self, job_id: str, metrics: dict, incomplete: bool = False) -> None:
        """Store eval metrics for a job."""

    def get_running_jobs_on_branch(self, branch: str) -> list[JobRecord]:
        """Check if any running job uses this experiment branch (for conflict prevention)."""
```

### 1.4 PostdocContext

The top-level object that wires everything together. All code receives this instead of individual backends.

```python
@dataclass
class PostdocContext:
    """Central context — the only thing CLI commands and agents need."""
    storage: StorageBackend
    scheduler: Scheduler
    tracker: JobTracker
    config: PostdocConfig       # parsed postdoc.yaml

def create_context(backend: str | None = None) -> PostdocContext:
    """Factory that reads postdoc.yaml and POSTDOC_BACKEND env var
    to assemble the right implementations.

    Resolution order:
    1. Explicit `backend` parameter
    2. POSTDOC_BACKEND env var
    3. `backend` field in postdoc.yaml
    4. Default: 'local'
    """
```

## 3. How Train/Eval Code Interacts with Storage

The training and eval scripts should **not** need to know about the storage backend. They write to local paths as they do today. The **wrapper script** (`run_job.py`) is the integration point:

1. Before training: wrapper creates the local job directory structure.
2. Training writes checkpoints/logs to local paths as usual (`--results_path results/<job-id>/training`).
3. After training (and periodically if cloud): wrapper calls `storage.put()` to persist artifacts.
4. Eval writes to local paths (`--store_dir results/<job-id>/eval/samples`).
5. After eval: wrapper extracts metrics and calls `storage.put_json()` for `metrics.json` and `meta.json`.

This means `train.py` and `final_valid.py` remain **unchanged** — they always write to local paths. The storage backend abstraction lives in the wrapper and CLI layer, not in the training code.

For the **cloud backend**, the wrapper additionally:
- Runs a checkpoint sync daemon that periodically calls `storage.put()` during training.
- Syncs all artifacts to R2 after completion.

```
train.py → writes to local path → wrapper → storage.put() → local FS or R2
```

## 4. Local Backend Implementation

### 4.1 LocalStorage

Trivial — `put()` writes to `<results_dir>/<job-id>/<rel_path>`, `get()` reads from it. `job_root_path()` returns the absolute local path.

### 4.2 LocalScheduler

- Tracks GPU allocation in the JobTracker DB (which GPUs are in use by which jobs).
- `submit()`: finds a free GPU, launches `run_job.py` via `nohup`, returns PID + GPU ID. If no GPU free, raises `NoCapacityError` — the CLI then marks the job QUEUED.
- `cancel()`: sends SIGTERM to the PID, releases the GPU.
- `is_alive()`: checks if PID is still running (`os.kill(pid, 0)`).
- `drain_queue()`: called after a job completes. Checks for queued jobs, launches the next one that fits available capacity.

### 4.3 Job Execution (run_job.py)

The wrapper script that both backends use (locally it runs directly, cloud runs it via bootstrap):

```python
def run_job(ctx: PostdocContext, job_id: str):
    job = ctx.tracker.get_job(job_id)

    # 1. Training
    ctx.tracker.update_state(job_id, JobState.TRAINING)
    train_result = run_training(job, ctx)
    if train_result.returncode != 0:
        ctx.tracker.update_state(job_id, JobState.FAILED,
            error_category=classify_error(train_result.stderr),
            error_message=tail(train_result.stderr))
        ctx.scheduler.drain_queue(ctx.tracker)
        return

    # 2. Eval
    ctx.tracker.update_state(job_id, JobState.EVAL)
    eval_result = run_eval(job, ctx)
    if eval_result.returncode != 0:
        ctx.tracker.update_state(job_id, JobState.FAILED,
            error_category=classify_error(eval_result.stderr),
            error_message=tail(eval_result.stderr))
        ctx.scheduler.drain_queue(ctx.tracker)
        return

    # 3. Extract metrics
    metrics, incomplete = extract_metrics(eval_result.stdout, job_id, ctx)
    ctx.tracker.set_metrics(job_id, metrics, incomplete)

    # 4. Finalize
    ctx.storage.put_json(job_id, PurePosixPath("meta.json"), build_meta(job))
    ctx.tracker.update_state(job_id, JobState.DONE)
    ctx.scheduler.drain_queue(ctx.tracker)
```

This same `run_job()` function is used by both backends. The only difference is how it's launched (nohup locally, bootstrap script on cloud) and whether checkpoint sync happens during training.

## 6. Package Structure

```
src/postdoc/
  __init__.py
  cli.py                    # Typer CLI — dispatches to context
  config.py                 # Load postdoc.yaml, create PostdocContext
  context.py                # PostdocContext, create_context() factory
  experiment.py             # Parse experiment YAML, merge configs
  run_job.py                # Shared job execution logic (training → eval → metrics)
  interfaces/
    __init__.py
    storage.py              # StorageBackend ABC
    scheduler.py            # Scheduler ABC, SchedulerSubmitResult
    tracker.py              # JobTracker (concrete, SQLite), JobState, JobRecord
  backends/
    __init__.py
    local/
      __init__.py
      storage.py            # LocalStorage(StorageBackend)
      scheduler.py          # LocalScheduler(Scheduler)
    cloud/                  # stub for now, implemented in full design
      __init__.py
      storage.py            # R2Storage(StorageBackend)
      scheduler.py          # SkyPilotScheduler(Scheduler)
```

Key points:
- `interfaces/` contains ABCs and the shared JobTracker
- `backends/` contains concrete implementations
- `cloud/` exists as a stub with `NotImplementedError` — proves the interface works and serves as a placeholder
- `run_job.py` is backend-agnostic — uses only `PostdocContext`

## 7. State Machine

Same states for both backends. The full design adds more failure-handling states later:

```
DEFINED → SUBMITTED → QUEUED → TRAINING → EVAL → COMPLETING → DONE
                                   |          |
                                 FAILED     FAILED
```

v0.1 uses this subset. The cloud backend will add LOCAL_REPRO / FIXING / RESUBMITTED / ESCALATED to `JobState` enum when implemented. Existing jobs in the DB are unaffected by new states being added.

## 10. Migration Path

Local → cloud is now **just adding a backend**:

1. Implement `R2Storage(StorageBackend)` and `SkyPilotScheduler(Scheduler)` in `backends/cloud/`.
2. Add failure-handling states to `JobState` enum.
3. Set `backend: cloud` in `postdoc.yaml` or `POSTDOC_BACKEND=cloud`.
4. Bulk-upload existing local results: `postdoc results push --all` (copies local storage to R2 via the storage interface).
5. Everything else — CLI, experiment YAMLs, agents, `run_job.py` — stays identical.
